### 0-1. 앱 받기 (8분)

💡 **왜 하나요?**
오늘 클로드 팀이 리뷰하고 고칠 **실습 대상**입니다. 일부러 **문제를 13개 심어둔** 작은 도서 대출 웹앱이라, 팀이 무엇을 찾아내는지 정답과 비교할 수 있습니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| `git clone` | GitHub 에 있는 저장소를 **통째로 내 컴퓨터에 복사** |
| 저장소 주소 | `https://github.com/아이디/저장소이름.git` 모양. clone 에는 **이 주소만** 넣을 수 있음 |

⌨️ **터미널**
```bash
mkdir -p ~/projects && cd ~/projects                         # 홈(~) 아래 projects 폴더를 만들고(-p = 이미 있으면 그냥 넘어감) 그 폴더로 이동. && = 앞 명령이 성공하면 뒤 명령 실행
git clone https://github.com/NujabesCode/library-app.git    # 연습용 앱 저장소를 내 컴퓨터로 복사 → library-app 폴더가 생김
cd library-app                                             # 받은 앱 폴더로 들어가기
git log --oneline                                          # 첫 커밋 1개가 보이면 정상 (오늘 실습 기록은 이 위에 쌓임)
```

⚠️ GitHub 화면의 **폴더 주소**(`.../tree/main/...`)를 넣으면 `repository not found`, 주소 뒤에 단어를 두 개 이상 붙이면 `Too many arguments` 에러가 납니다. **위 명령 그대로** 복사하세요.

👀 **확인할 것**: `git log --oneline` 에 `init: 팀 에이전트 실습용 도서 대출 앱` 한 줄이 보이면 성공


<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

이 단계가 끝나면 `~/projects/library-app` 폴더가 생기고, `git log --oneline` 에 커밋이 딱 한 줄 보입니다. 오늘 학생들이 남기는 커밋은 모두 이 한 줄 위에 쌓이므로, 하루가 끝났을 때 `git log` 만 보면 무엇을 했는지 그대로 남습니다.

연습용 앱을 강의 자료 저장소(Harness)와 따로 둔 이유는, 학생이 받는 저장소에 정답지와 강의 PDF가 섞이지 않게 하기 위해서입니다. 이 앱에는 보안 6개, 성능·안정성 4개, 로직 2개, 테스트 부족 1개, 모두 13개의 문제가 일부러 심어져 있습니다. 정답 목록과 채점 방법은 블록 3-4 에 있습니다.

clone 에서 가장 많이 나는 에러는 두 가지입니다. GitHub 화면에서 폴더를 클릭한 주소(`.../tree/main/...`)를 넣으면 그건 저장소 주소가 아니라서 `repository not found` 가 나고, 주소 뒤에 폴더 이름을 두 개 이상 붙이면 `Too many arguments` 가 납니다. 둘 다 위 명령을 그대로 복사하면 해결됩니다.

</div>

### 0-2. 실행해보기 (7분)

💡 **왜 하나요?**
리뷰 전에 **앱이 원래 어떻게 동작하는지** 직접 눌러봐야, 나중에 팀이 "고쳤다" 고 할 때 무엇이 달라졌는지 알 수 있습니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| `npm test` | `package.json` 에 적힌 **테스트 실행 명령**(`node --test`)을 돌림 → `test/` 폴더의 테스트 실행 |
| `npm start` | `package.json` 에 적힌 **시작 명령**(`node server.js`)을 돌림 → 웹 서버가 켜짐 |
| `localhost:3000` | **내 컴퓨터**(localhost)의 3000번 문(포트)에서 켜진 웹사이트 |
| Ctrl + C | 터미널에서 실행 중인 프로그램(서버)을 **끄기** |

⌨️ **터미널**
```bash
npm test    # 테스트 실행 → "pass 2" 가 보이면 정상
npm start   # 서버 시작 → 브라우저에서 http://localhost:3000 접속. 끌 때는 Ctrl + C
```
브라우저에서: **가입 → 로그인 → 검색 → 대출 → 반납** 눌러보기 → 터미널로 돌아와 **Ctrl + C** 로 서버 끄기

⌨️ **터미널** (서버를 끈 다음)
```bash
git checkout data/books.json   # 눌러 보느라 바뀐 책 데이터를 처음 상태로 되돌리기
```

👀 **확인할 것**: 테스트 `pass 2`, 브라우저에 책 5권 목록

⚠️ 이 앱에는 **일부러 심어둔 문제가 13개** 있습니다. 지금 찾지 말고, 오늘 클로드 팀이 찾게 합니다.


<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

`npm test` 는 `pass 2` 로 통과합니다. 그런데 이건 앱이 멀쩡하다는 뜻이 아닙니다. 테스트가 "제목으로 검색된다"와 "빌리면 권수가 1 줄어든다" 두 가지 정상 경로만 확인하기 때문에, 심어 둔 13개 문제 중 어느 것도 잡지 못합니다. 학생들에게 "테스트가 통과했는데 문제가 13개 있다"는 사실을 먼저 짚어 주면, 오후에 테스트를 늘리고 검문소(hook)를 다는 이유가 자연스럽게 연결됩니다.

대출·반납을 눌러 보면 `data/books.json` 파일 내용이 실제로 바뀝니다. 이 앱은 git 이 관리하는 데이터 파일에 바로 저장하기 때문입니다. 그대로 두면 두 가지 문제가 생깁니다. 첫째, 이후 리뷰에서 클로드가 "데이터가 이미 어긋나 있다"는 보고를 덧붙여서 결과가 반마다 달라집니다. 둘째, 휴식 때 `git add .` 를 하면 이 변경까지 커밋됩니다. 그래서 서버를 끈 직후 `git checkout data/books.json` 으로 되돌립니다.

</div>

### 0-3. 오늘의 목표 선언 (5분)
> "오늘은 클로드를 **한 명이 아니라 팀으로** 부립니다. 그리고 **언제 팀을 쓰면 안 되는지**도 배웁니다. 팀은 비쌉니다."

교재의 **혼자 · 심부름꾼 · 팀** 표를 같이 읽기

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

세 방식의 차이는 "누가, 몇 명이, 서로 대화하는가"입니다.

**혼자**는 클로드 한 명이 한 머릿속에서 처음부터 끝까지 하는 방식입니다. 가장 싸고, 일이 작거나 A 다음 B 처럼 순서대로 이어질 때 가장 낫습니다.

**심부름꾼**은 메인 클로드가 일부를 다른 클로드에게 맡기고 결과 요약만 돌려받는 방식입니다. 과정은 길지만 결과만 필요한 일(파일 수십 개 훑기, 긴 로그 읽기, 테스트 돌리기)에 좋습니다. 심부름꾼끼리는 대화하지 않고, 일이 끝나면 보고하고 사라집니다.

**팀**은 독립된 클로드 여러 명이 각자 일하면서 서로 메시지를 주고받는 방식입니다. 팀원 한 명이 클로드 한 명이므로 사용량은 팀원 수만큼 늘어납니다. 그래서 서로 반박하거나 확인해야 값어치가 생기는 일(기획 회의, 원인 모르는 버그, 깊이 있는 리뷰)에서만 비용만큼 이득을 봅니다.

오늘 실습은 이 세 문장을 학생이 직접 해 보고, 블록 3 에서 숫자로 확인하는 과정입니다.

</div>

## 블록 1 | 심부름꾼(서브에이전트) 복습 (40분)

### 목표
팀을 쓰기 전에, 더 가볍고 싼 **심부름꾼** 으로 할 수 있는 걸 먼저 써보기

> 💡 **이 블록을 먼저 하는 이유**: 팀 에이전트는 비쌉니다. 많은 일은 **심부름꾼 한 명**으로 충분합니다. 심부름꾼이 뭔지 알아야 "이건 팀이 필요한 일인가?" 를 판단할 수 있습니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| 서브에이전트 (Subagent) | **심부름꾼.** 메인 클로드가 곁가지 일을 다른 클로드에게 보내고 **결과 요약만** 돌려받는 방식 |
| 메인 클로드 | 내가 대화창에서 대화하고 있는 클로드 |
| 컨텍스트 (머릿속) | 클로드가 한 번에 기억하는 대화·파일 내용. 너무 많이 쌓이면 헷갈리고 비싸짐 |

### 1-1. 기본 심부름꾼 써보기 (8분)

💡 **왜 하나요?**
Claude Code 에는 **이미 만들어진 심부름꾼**이 있습니다. 그중 **Explore** 는 파일을 **읽기만** 하는 탐색 전문가입니다. 파일 수십 개를 메인 클로드가 직접 열면 그 내용이 전부 대화에 쌓이지만, Explore 에게 시키면 **탐색은 심부름꾼 머릿속에서** 하고 **깔끔한 요약만** 돌아옵니다. 이 "보내고 → 요약만 받는" 느낌을 처음 체험하는 단계입니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| Explore | Claude Code 에 **기본으로 들어 있는** 읽기 전용 탐색 심부름꾼 |
| 프로젝트 구조 | 어떤 파일·폴더가 있고 각자 무슨 일을 하는지 |

⌨️ **터미널**
```bash
claude   # 이 폴더에서 Claude Code 대화 시작 → 화면이 클로드 대화창으로 바뀜
```
💬 **클로드 대화창**
```
Explore 서브에이전트로 이 프로젝트 구조를 파악해서, 파일마다 하는 일을 한 줄씩 표로 정리해줘.
```

👀 **확인할 것** (버전마다 모양은 조금씩 다름)
```
● Explore(프로젝트 구조 파악)                ← ① 메인 클로드가 심부름꾼을 보냈다는 표시
  ⎿  Read(server.js)                        ← ② 심부름꾼이 파일을 읽는 중
     +5 more tool uses                      ← 나머지는 접혀 있음
  ⎿  Done (8 tool uses · 18k tokens · 25s)  ← ③ 끝. 도구 8번 사용, 25초
● | 파일 | 하는 일 | ...                     ← ④ 메인 클로드는 요약 표만 받음
```
| 보는 곳 | 뜻 |
|---|---|
| `● Explore(...)` 줄 | 메인이 직접 안 하고 **심부름꾼을 보냈다** |
| `Read(...)` 가 지나가다 접힘 | 파일 읽기는 **심부름꾼 머릿속**에서만. 메인 대화엔 안 쌓임 |
| `Done (...)` 다음에 **표만** | **요약만** 돌아왔다 |

> 💡 **Ctrl + O** 로 접힌 내용을 펼쳐서 심부름꾼이 한 일을 자세히 볼 수 있습니다 (다시 누르면 접힘)

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

Explore 가 돌려주는 표는 대략 아래와 같습니다. 표현은 반마다 조금씩 다르지만 파일 8개와 역할은 같아야 정답입니다.

| 파일 | 하는 일 |
|---|---|
| `package.json` | 실행 명령(`npm start`)과 테스트 명령(`npm test`) 정의 |
| `server.js` | 웹 서버. API 주소 연결, 화면 파일 보내기 |
| `src/books.js` | 책 검색, 대출, 반납, 연체료 계산 |
| `src/auth.js` | 회원가입, 로그인, 토큰 확인 |
| `public/index.html` | 브라우저 화면 |
| `data/books.json` | 책 5권 데이터 (재고 포함) |
| `test/books.test.js` | 테스트 2개 (검색, 대출) |
| `README.md` | 앱 설명과 API 목록 |

화면을 보면 Explore 가 파일을 8번 정도 읽었는데, 메인 대화에는 표 하나만 남습니다. 메인 클로드가 직접 읽었다면 파일 내용이 전부 대화에 쌓입니다. 대화에 쌓인 내용은 다음 질문을 할 때마다 다시 읽히기 때문에 그만큼 사용량이 들고, 대화가 길어질수록 클로드가 앞 내용을 헷갈립니다.

그래서 결론은 이렇습니다. **과정은 길지만 결과만 필요한 일은 심부름꾼에게 맡긴다.** 이게 팀을 꺼내기 전에 먼저 떠올려야 할 가장 싼 방법입니다.

### 1-2. 역할 카드 만들기 (15분)

💡 **왜 하나요?**
Explore 같은 기본 심부름꾼 말고, **내가 원하는 역할의 심부름꾼**을 만들 수 있습니다. 한 번 파일로 만들어두면 매번 "너는 테스트 담당이고, 코드는 고치지 말고…" 라고 설명할 필요가 없습니다. 여기서 만든 **test-runner** 는 블록 5-4 에서 팀이 고친 코드를 검사할 때 **다시 부르고**, 같은 방법으로 블록 3 에서 **팀원용 역할 카드**를 만듭니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| `.claude/agents/` | 이 프로젝트용 역할 카드를 두는 폴더. 파일 하나 = 심부름꾼 하나 |
| 역할 카드 파일 | 위쪽 `---` 사이에 **설정**, 아래에 **업무 지시** 를 적은 `.md` 파일 |
| frontmatter | 파일 맨 위 `---` 와 `---` 사이의 **설정 부분** |
| `description` | **언제 이 심부름꾼을 부를지** 설명. 클로드가 이걸 읽고 알아서 부름 |
| `tools` | 이 심부름꾼이 **쓸 수 있는 도구 목록**. 적힌 것만 사용 가능 |
| `model` | 이 심부름꾼이 쓸 **두뇌(모델)** |
| 본문 | `---` 아래 내용. 심부름꾼이 받는 **업무 지시서** |

📖 **도구 (tools) 풀이** — 클로드가 일할 때 쓰는 손발입니다
| 도구 | 하는 일 | 비유 |
|---|---|---|
| **Read** | 파일 **내용을 읽기** | 책 펼쳐 읽기 |
| **Grep** | 여러 파일 **안에서 글자 찾기** (예: `borrowBook` 이 어디 쓰였나) | Ctrl + F 를 폴더 전체에 |
| **Glob** | **파일 이름 모양으로** 파일 찾기 (예: `test/*.js` → test 폴더의 js 파일 전부) | 탐색기에서 `*.js` 로 검색 |
| **Bash** | **터미널 명령 실행** (예: `npm test`) | 터미널에 직접 타이핑 |
| Edit / Write | 파일 **고치기** / **새로 쓰기** | 펜으로 고쳐 쓰기 |

> 💡 **일부러 Edit 와 Write 를 빼는 이유**: "코드는 고치지 마" 라고 **말로만** 하면 클로드가 가끔 고칩니다. 도구 목록에서 **아예 빼버리면** 고치고 싶어도 못 고칩니다. 말이 아니라 **구조로 막는** 것입니다.

📖 **모델 (model) 풀이**
| 값 | 특징 |
|---|---|
| `sonnet` | 빠르고 비용이 적당. **오늘 기본값** |
| `opus` | 가장 똑똑하지만 비쌈. 어려운 판단용 |
| `haiku` | 가장 빠르고 쌈. 단순 작업용 |
| `inherit` | 메인 클로드와 같은 모델 |

💬 **클로드 대화창**
```
.claude/agents/test-runner.md 서브에이전트를 만들어줘.
- description: 테스트를 실행하고 실패 원인을 요약할 때 사용
- tools: Read, Grep, Glob, Bash
- model: sonnet
- 본문: npm test 를 실행하고, 실패하면 원인과 파일:줄만 보고해. 코드는 절대 고치지 마.
```

👀 **확인할 것**: 만들어진 파일을 열어서 (VS Code 에서 `.claude/agents/test-runner.md`) 아래 모양인지 같이 읽기
```markdown
---
name: test-runner
description: 테스트를 실행하고 실패 원인을 요약할 때 사용
tools: Read, Grep, Glob, Bash
model: sonnet
---

npm test 를 실행하고, 실패하면 원인과 파일:줄만 보고해. 코드는 절대 고치지 마.
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

결과로 `.claude/agents/test-runner.md` 파일이 위 모양으로 생기면 정답입니다. 줄마다 의미는 이렇습니다. `name` 은 부를 때 쓰는 이름, `description` 은 클로드가 "언제 이 심부름꾼을 보낼지" 판단하는 기준, `tools` 는 쓸 수 있는 도구 목록, `model` 은 심부름꾼의 두뇌, `---` 아래 본문은 업무 지시서입니다.

`tools` 에서 Edit 와 Write 를 뺀 것이 이 단계의 핵심입니다. 본문에 "고치지 마"라고 쓰는 건 말로 부탁하는 것이라 가끔 무시되지만, 도구를 아예 안 주면 고치고 싶어도 못 고칩니다. 다만 Bash 가 남아 있으면 터미널 명령으로 파일을 바꾸는 길은 열려 있기 때문에, 본문의 "고치지 마"도 같이 적어 두는 겁니다. **구조로 막고, 말로도 한 번 더 막는다**고 설명하면 됩니다.

test-runner 를 예로 고른 이유는 테스트 확인이 하루에도 여러 번 반복되는 일이고, **고치는 사람과 검사하는 사람이 달라야** 하는 일이기 때문입니다. 그래서 블록 5-4 에서 팀이 코드를 고친 뒤 이 카드를 다시 불러 검사합니다.

학생이 VS Code 로 파일을 직접 만들었다면, 클로드를 껐다 켜야 목록에 나타납니다. 클로드는 켜질 때 `.claude/agents/` 를 읽기 때문입니다. 대화창에서 `/agents` 로 만들면 바로 등록됩니다.

</div>

### 1-3. 지목해서 부르기 (7분)

💡 **왜 하나요?**
그냥 "테스트 돌려줘" 라고 하면 클로드가 **직접** 할 수도, 심부름꾼을 **보낼** 수도 있습니다. `@` 로 지목하면 **반드시 그 심부름꾼이** 일합니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| `@` 멘션 | 대화창에서 `@` 를 치면 파일·심부름꾼 목록이 뜸 → 골라서 **콕 집어 부르기** |

💬 **클로드 대화창**: `@` 를 입력 → 목록에서 `test-runner (agent)` 선택 → 이어서 입력
```
@"test-runner (agent)" 테스트 돌려줘
```
👀 **확인할 것**: `● test-runner(...)` 줄이 생기고, 결과로 "2개 통과" 같은 요약만 돌아옴


<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

결과는 "테스트 2개 모두 통과" 정도의 짧은 요약입니다. 테스트 출력 전체가 아니라 요약만 오는 게 심부름꾼다운 결과입니다.

`@` 를 쳐도 test-runner 가 목록에 안 뜨는 학생이 꼭 나옵니다. 원인은 거의 넷 중 하나입니다. 첫째, 파일을 만든 뒤 클로드를 다시 켜지 않았습니다(가장 흔함, `/exit` 후 `claude`). 둘째, 폴더나 이름이 틀렸습니다(`.claude/agents/` 가 아니거나 `.md.txt` 로 저장됨). 셋째, 파일 첫 줄이 `---` 가 아닙니다(앞에 빈 줄이나 코드블록 기호가 섞임). 넷째, 목록에 있는데 파일 목록에 묻혀서 안 보입니다(`@test` 까지 쳐서 거르기). 대화창에서 `/agents` 를 입력하면 등록된 심부름꾼 목록이 나오므로, 거기 있는지부터 확인하게 하세요.

`@` 로 지목하는 이유는 `description` 만으로는 클로드가 그 심부름꾼을 부를지 확실하지 않기 때문입니다. "테스트 돌려줘"라고만 하면 클로드가 직접 `npm test` 를 칠 수도 있습니다. 반드시 그 역할에게 시키고 싶을 때는 이름으로 부릅니다.

</div>

### 1-4. 백그라운드로 보내기 (10분)

💡 **왜 하나요?**
심부름꾼이 일하는 동안 기다리기만 하면 시간이 아깝습니다. **백그라운드**로 보내면 심부름꾼은 뒤에서 일하고, 나는 그동안 **다른 질문**을 할 수 있습니다. 팀 에이전트의 "여럿이 동시에 일한다" 감각의 맛보기입니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| 포그라운드 | 심부름꾼이 끝날 때까지 **대화가 멈춰서 기다림** (기본) |
| 백그라운드 | 심부름꾼은 **뒤에서** 일하고, 나는 계속 대화 가능 |
| Ctrl + B | 지금 실행 중인 일을 **백그라운드로 보내기** |

💬 **클로드 대화창**
```
test-runner 서브에이전트로 테스트를 돌리고, src 폴더에 테스트가 없는 함수 목록도 찾아줘.
```
→ 심부름꾼이 일하기 시작하면 바로 **Ctrl + B** → 입력창이 다시 열리면:
```
README 를 읽고 API 목록을 한 줄로 요약해줘.
```
👀 **확인할 것**: README 요약이 먼저 오고, **심부름꾼 결과가 나중에 따로 도착**

💬 **강사 질문**: "test-runner 는 결과만 돌려줬어요. **다른 심부름꾼과 상의**했나요?" → 아니요. 심부름꾼은 **보고만** 합니다. 서로 상의하고 반박하는 건 **팀**만 할 수 있습니다 (교재 2단계 표)

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

README 요약은 몇 초 만에 먼저 옵니다. 정답은 API 5개입니다. 책 검색(`GET /api/books?q=`), 회원가입(`POST /api/signup`), 로그인 후 토큰 발급(`POST /api/login`), 토큰이 필요한 대출(`POST /api/books/:id/borrow`), 연체료가 함께 오는 반납(`POST /api/books/:id/return`)입니다.

test-runner 결과는 나중에 따로 도착합니다. 정답은 "테스트 2개 통과, 테스트가 없는 함수는 `returnBook`, `lateFee`, `signup`, `login`, `verify`"입니다. 지금 테스트는 `searchBooks` 와 `borrowBook` 만 부릅니다. `loadBooks`, `saveBooks` 는 그 안에서 간접적으로만 쓰입니다.

학생들은 이 단계에서 "동시에 하는 게 아니라 하나 끝나고 하나 하는 것 같다"고 자주 말합니다. 실제로는 동시에 돈 것이고, README 가 파일 하나만 읽으면 끝나는 짧은 일이라 먼저 끝났을 뿐입니다. 화면에 증거가 있습니다. README 답이 먼저 나오고, 그 아래 `Waiting for 1 background agent to finish` (뒤에서 1명이 아직 일하는 중)가 뜬 뒤, `Message from @test-runner` 로 결과가 도착합니다. 순서대로 했다면 먼저 시킨 test-runner 보고가 먼저 왔어야 합니다. 화면에 `Resuming agent ...` 가 보이면 test-runner 를 새로 만든 게 아니라 1-3 에서 쓴 것을 다시 불러온 것입니다.

Ctrl + B 로 뒤로 보낼 수 있는 건 **심부름꾼**과 **터미널 명령** 두 가지뿐입니다. 메인 클로드가 직접 생각하고 답을 쓰는 중에는 Ctrl + B 가 듣지 않습니다. 메인 클로드는 한 명이라 한 번에 한 가지만 생각하기 때문입니다. 그래서 "생각이 필요한 일까지 통째로 뒤에 맡기려면 심부름꾼이 필요하다"가 이 단계의 결론입니다. 그리고 강사 질문의 답처럼, 동시에 일하는 것까지는 심부름꾼도 되지만 **서로 대화하며 일하는 건 팀만** 됩니다. 블록 2 로 넘어가는 이유가 이것입니다.

</div>

## 블록 2 | 팀 켜기 + 첫 팀 (30분)

### 목표
팀 기능을 켜고, 팀원이 일하는 모습을 **현황판**으로 들여다보는 연습

📖 **용어**
| 말 | 뜻 |
|---|---|
| 팀 에이전트 (Agent Teams) | 클로드 여러 명이 **한 팀**으로 일하는 기능. 서로 메시지로 대화함 |
| 팀장 (Lead) | 내가 대화하는 원래 클로드. 팀원을 뽑고 일을 나누고 결과를 합침 |
| 팀원 (Teammate) | 팀장이 뽑은 **독립된 클로드**. 각자 자기 머릿속에서 일함 |
| 현황판 (Agent panel) | 입력창 **아래** 팀원 목록. 누가 일하는 중인지 보임 |

### 2-1. 팀 기능 켜기 (7분)

💡 **왜 하나요?**
팀 에이전트는 아직 **실험 기능**이라 **기본으로 꺼져** 있습니다. 설치할 건 없고, **설정 파일에 한 줄**만 넣으면 켜집니다. **이 프로젝트에서만** 켜는 이유는, 전체 설정에 켜두면 다른 프로젝트에서도 클로드가 마음대로 팀을 꾸려 사용량이 새기 때문입니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| `.claude/settings.json` | **이 프로젝트용** Claude Code 설정 파일 |
| `env` | 환경 변수 (프로그램에게 주는 스위치) 를 적는 칸 |
| `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS` | 팀 기능 스위치. `"1"` = 켜기, `"0"` = 끄기 |
| `/exit` | 클로드 대화를 끝내고 터미널로 돌아가기 |

💬 **클로드 대화창**
```
이 프로젝트의 .claude/settings.json 에 env 로 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1 을 추가해줘.
기존 설정이 있으면 합쳐줘. 저장 후 파일 전체를 보여줘.
```
👀 **확인할 것**: 이 내용이 들어 있으면 성공
```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```
💬 `/exit` → ⌨️ 다시 `claude` (새 설정으로 깨끗하게 시작)

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

결과로 `.claude/settings.json` 에 위 JSON 이 들어가면 정답입니다. 설치는 필요 없습니다. Claude Code 에 이미 들어 있는 기능을 스위치로 켜는 것뿐입니다.

반드시 껐다 켜야 하는 이유는 클로드가 **켜질 때** 설정 파일을 읽기 때문입니다. 껐다 켜지 않으면 이후 2-2 에서 팀 대신 심부름꾼이 생기고, 현황판에서 ↓ 를 눌러도 아무것도 안 뜨는 증상이 나옵니다. 오후까지 "팀이 안 만들어져요"라는 질문의 대부분이 이 재시작 누락입니다.

이 프로젝트에만 켜는 이유도 설명해 주세요. 이 스위치가 켜져 있으면 클로드가 스스로 이름을 붙여 보낸 심부름꾼이 팀원으로 뜨는 경우가 있어서, 팀을 원하지 않은 프로젝트에서도 사용량이 늘 수 있습니다.

</div>

### 2-2. 첫 팀: 예약 기능 기획 회의 (15분)

💡 **왜 하나요?**
첫 팀은 **코드를 고치지 않는 일**(기획)로 시작합니다. 코드 수정은 팀원끼리 같은 파일을 건드리는 사고가 날 수 있지만, 기획은 **각자 다른 관점에서 동시에 생각**만 하면 되니 실패할 일이 적습니다. 오후에 실제로 만들 **"예약 기능"** 을 미리 설계해 둡니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| 예약 기능 | 재고가 0인 책을 예약해두면, 반납될 때 **순서대로** 받을 수 있는 기능 |
| 악마의 변호인 (critic) | 일부러 **반대 의견**을 내서 빠뜨린 문제를 찾는 역할 |
| `docs/` | 기획·리뷰 문서를 모아둘 폴더 (클로드가 만들어 줌) |

💬 **클로드 대화창**
```
이 도서 대출 앱에 "예약 기능"(재고가 0인 책을 예약해두면 반납될 때 순서대로 받을 수 있는 기능)을 추가하려고 해.
agent team 으로 팀원 3명을 뽑아줘. 이름은 ux, arch, critic, 모델은 모두 Sonnet.
- ux: 사용자 입장에서 화면 흐름과 안내 문구
- arch: 데이터 구조와 API 설계 (src/books.js, server.js 기준)
- critic: 악마의 변호인. 이 기능의 문제점과 빠뜨린 경우를 찾기
코드는 고치지 말고, 결과를 합쳐서 docs/reservation-plan.md 에 써줘.
```
> 💡 **"agent team 으로" 를 꼭 넣는 이유**: 안 넣으면 클로드가 팀 대신 **심부름꾼**을 쓸 때가 있습니다. 둘은 현황판에 같이 보여서 헷갈립니다.

⚠️ 기획 팀은 **1~2분 만에** 끝나기도 합니다. 프롬프트를 보내자마자 **바로 2-3** (↓ → Enter) 을 시작하세요.

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

결과로 `docs/reservation-plan.md` 가 생깁니다. 실제로 돌려 본 결과에서 "팀이라서 생긴 것"을 학생에게 짚어 줄 부분은 세 가지입니다.

첫째, **의견마다 누가 냈는지 표시**되어 있습니다. "(arch 제안, critic 조건부 찬성)", "(critic E4)"처럼 출처가 붙습니다. 혼자 쓴 문서에는 이런 흔적이 없습니다.

둘째, **팀원끼리 반박해서 결론이 바뀐 흔적**이 남습니다. 실제 결과에서 arch 는 처음에 "남은 권수(`available`)를 파일에 저장하자"고 했고, critic 이 "그러면 파일을 손으로 고치거나 중간에 실패할 때 다시 어긋난다"고 반박해서, 최종안은 "남은 권수는 저장하지 않고 그때그때 계산한다"로 바뀌었습니다. 혼자 하면 처음 떠올린 안으로 그냥 가는 경우가 많습니다. 이게 팀을 쓰는 가장 큰 이유입니다.

셋째, **"이 기능이 정말 필요한가?"라는 질문**이 나옵니다. critic 은 알림 기능이 없는데 보관 기한을 두는 모순을 지적하고, 대안 네 가지를 비교한 뒤 "예약보다 재고 버그와 토큰 위조부터 고쳐라"고 권했습니다. 만드는 쪽 관점만 있으면 이런 질문은 잘 안 나옵니다.

기획이 첫 팀 과제로 좋은 이유는 관점끼리 독립적이고 파일을 고치지 않아 사고가 날 일이 없기 때문입니다. 단, 이 기획안의 판단은 대부분 코드를 **읽고** 내린 것이지 실행해서 확인한 것은 아니라는 점도 같이 말해 주세요. "확인"의 차이는 블록 3 에서 숫자로 드러납니다.

</div>

### 2-3. 현황판 조작 연습 (8분) — 팀이 일하는 동안

💡 **왜 하나요?**
팀장만 보고 있으면 팀원이 **엉뚱한 방향으로 오래 달리는 걸** 놓칩니다. 현황판에서 팀원 화면을 들여다보고 직접 말을 거는 게 팀 운영의 기본입니다.

| 해보기 | 키 | 설명 |
|---|---|---|
| 팀원 고르기 | **↑ / ↓** | 입력창 **아래** 현황판에서 |
| 그 팀원 화면 보기 | **Enter** | 그 팀원이 지금까지 한 일 + **직접 말 걸기** 가능 |
| 팀장 화면으로 돌아오기 | **Esc** | ⚠️ 팀원 화면에서 Esc 는 **그 팀원 작업을 멈춤** → 실험해보고 "계속해" 라고 말해주기 |
| 할 일 보드 | **Ctrl + T** | 팀 전체의 할 일 목록 (대기 / 진행 중 / 완료) |

📖 **용어**
| 말 | 뜻 |
|---|---|
| 팀원 화면 (예: critic 화면) | **팀원 한 명의 대화창.** 그 팀원이 읽은 파일과 생각이 다 보이고, 여기서 입력하면 팀장을 거치지 않고 그 팀원에게 바로 전달됨 |
| critic | 영어 단어 그대로 **비평가.** 줄임말 아님 (ux = 사용자 경험, arch = architect 설계자) |

⚠️ 입력창에서 **↑** 는 이전에 쓴 문장(히스토리)이 나옵니다. **입력창을 비운 채 ↓** 를 눌러야 현황판으로 내려갑니다.

→ critic 화면에 들어가서 (↑↓ 로 고르고 Enter) 💬 직접 말 걸기:
```
초등학생이 쓴다고 생각하고 문제점을 하나 더 찾아봐.
```
끝나면 💬 팀장 화면에서:
```
팀원 모두 퇴근시켜줘.
```
> 💡 **퇴근시키는 이유**: 팀원은 일이 끝나도 살아 있는 동안 계속 사용량을 씁니다.

👀 **확인할 것**: 현황판에 `ux`, `arch`, `critic` 3명 / `docs/reservation-plan.md` 파일 생성

⚠️ 팀원 줄이 갑자기 사라져도 **죽은 게 아닙니다.** 모두가 쉬면 30초 뒤 **숨겨질** 뿐입니다.

🆘 현황판이 이미 비어 있으면 💬 팀장에게: `critic 팀원에게 메시지를 보내줘: 초등학생이 쓴다고 생각하고 문제점을 하나 더 찾아봐` → critic 이 깨어나 줄이 다시 생기면 ↓ → Enter

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

이 단계에서 가장 많이 막히는 곳은 "↓ 를 눌러도 아무것도 안 뜬다"입니다. 원인은 거의 항상 **팀이 이미 일을 끝냈기 때문**입니다. 기획 팀은 1~2분 만에 끝나고, 모든 팀원이 쉬면 30초 뒤 현황판에서 숨겨집니다. 이때 학생이 입력창에 "초등학생이 쓴다고 생각하고..."를 그냥 치면, critic 이 아니라 **팀장**이 그 말을 받아서 직접 처리합니다. 실제 수업에서도 화면에 `Read 1 file`, `Update(docs/reservation-plan.md)` 가 떴는데, 이건 팀장이 한 일이었습니다. 그래서 팀장에게 "critic 팀원에게 메시지를 보내줘"라고 이름으로 부탁해야 critic 이 깨어납니다. 깨어나면 줄이 다시 생기니 그때 ↓ → Enter 로 들어가면 됩니다.

↓ 를 눌러도 안 뜨고, 팀장에게 이름으로 보내도 "그런 팀원이 없다"는 답이 오면 팀이 처음부터 안 만들어진 겁니다. 2-1 의 설정과 재시작, 2-2 프롬프트의 "agent team 으로"를 확인하게 하세요.

critic 이 찾는 추가 문제의 예(실제 결과)는 이렇습니다. 교실 공용 PC 에서는 로그아웃 버튼이 없고 로그인 토큰이 기한 없이 남아서, 뒷사람이 자기도 모르게 앞사람 계정으로 예약하거나 취소할 수 있다는 지적이었습니다. 여기에 "보관", "수령", "기한" 같은 단어가 초등학생에게 어렵다는 점, 금요일에 반납된 책은 3일 보관 기한이 주말에 끝나 버린다는 점까지 나왔습니다. 기획안에 "공용 PC 대응" 절이 새로 붙으면 정답입니다.

팀원 화면에 직접 말을 거는 게 좋은 이유는, 그 팀원이 지금까지 읽은 파일과 생각을 그대로 가진 채 방향만 바꿀 수 있기 때문입니다. 팀장을 거치면 팀장이 말을 요약해서 전달하기 때문에 뜻이 조금씩 바뀌고, 한 번 더 기다려야 합니다.

</div>

## 블록 3 | 🔍 리뷰 팀 — 혼자 vs 팀 대결 (50분)

### 목표
같은 코드를 **혼자 리뷰** 한 것과 **팀으로 리뷰** 한 것을 비교해서, 팀이 **언제 이득인지** 숫자로 확인

> 💡 **이 블록이 오늘의 핵심인 이유**: "팀이 좋다" 는 말만 들으면 모든 일에 팀을 씁니다. 같은 일을 두 방식으로 해보고 **찾은 개수**와 **쓴 사용량**을 나란히 놓아야 판단 기준이 생깁니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| 코드 리뷰 | 코드를 읽고 **문제점을 찾아 보고**하는 일 (고치지는 않음) |
| 심각도 | 문제가 얼마나 급한지: 높음 / 중간 / 낮음 |
| 재현 | 문제가 **진짜로 일어나는지** 실제로 실행해서 보여주기 |

### 3-1. 🧑 혼자 리뷰 (10분) — 기준점

💡 **왜 하나요?** 팀과 비교할 **기준 점수**를 만듭니다. **새 터미널**에서 하는 이유는 앞에서 나눈 대화(기획 회의 내용)가 섞이지 않은 **깨끗한 클로드**로 리뷰해야 공정하기 때문입니다.

⌨️ **새 터미널**을 하나 더 열고
```bash
cd ~/projects/library-app && claude   # 앱 폴더로 이동한 뒤 새 클로드 대화 시작
```
💬 **클로드 대화창**
```
이 앱의 문제점을 리뷰해줘. 보안, 성능, 버그, 테스트 부족 무엇이든.
서브에이전트나 팀은 쓰지 말고 너 혼자 해줘. 코드는 고치지 말고,
문제마다 한 줄씩 번호를 매겨서 docs/review-solo.md 에 써줘.
```
👀 **확인할 것**: 몇 개 찾았는지 **숫자를 칠판에** 적기 → 💬 `/exit` 로 이 터미널은 닫기

결과를 문장으로 정리하면 이렇습니다.

**찾은 개수는 비겼습니다.** 혼자도 팀도 심어 둔 13개를 다 찾았고, 문제 목록 전체로는 오히려 혼자가 44개로 더 많았습니다. 파일 7개짜리 작은 앱은 클로드 한 명의 머릿속에 다 들어가기 때문에, 혼자서도 넓게 볼 수 있습니다.

**믿을 수 있는 정도는 팀이 이겼습니다.** 점수 차이 10점은 전부 "직접 실행해서 확인했나"에서 났습니다. 팀원은 각자 맡은 파일만 깊게 보니까 서버를 띄우고 공격 요청을 보내 볼 여유가 생겼고, 그 과정에서 혼자 리뷰의 거짓 경보(`__proto__`)도 걸러졌습니다. 혼자 리뷰를 그대로 믿고 고쳤다면, 실제로는 안 뚫리는 곳을 고치느라 시간을 썼을 겁니다.

**범위는 혼자가 이겼습니다.** 팀은 일을 나눈 탓에 아무도 맡지 않은 경계(auth 테스트, 화면 동작 버그)를 놓쳤고, 팀장이 메웠습니다. 팀을 쓸 때는 "이 범위 나누기에서 빠진 곳이 없나"를 팀장이나 내가 꼭 확인해야 합니다.

**사용량은 팀이 몇 배였습니다.** `/usage` 로 혼자 리뷰를 한 터미널과 팀 리뷰를 한 터미널의 사용량을 비교하면, 팀원 3명에 팀장까지 돌아가므로 보통 몇 배가 나옵니다.

그래서 강사 질문의 답은 이렇게 정리됩니다. "팀이 더 **많이** 찾지는 않았다. 더 **확실하게** 찾았다. 그 대신 몇 배를 썼다. 그러니 매번 팀을 쓰지는 않는다. 이 정도 작은 앱의 1차 점검은 혼자로 충분하고, 배포 직전처럼 '진짜로 일어나는지'가 중요하거나, 코드가 커서 한 명이 다 못 보는 경우에 팀을 쓴다."

학생들에게 이렇게 물어보면 결론을 스스로 말하게 할 수 있습니다. "내일 이 앱을 실제로 배포한다면 어느 리뷰를 믿겠어요?" 그리고 "팀이 놓친 화면 버그는 범위를 어떻게 나눴으면 잡았을까요?" 두 번째 질문의 답은 "화면 동작 담당 팀원을 하나 더 두거나, `index.html` 의 동작 버그를 누군가에게 명시적으로 맡긴다"입니다.

## 블록 4 | 💬 토론 + 직접 대화 (40분)

### 목표
팀원끼리 **서로 반박**하게 해서 리뷰 결과를 다듬고, **고칠 순서**를 정하기

> 💡 **이 블록을 하는 이유**: 심부름꾼은 보고만 하고 끝나지만, 팀원은 **서로의 결과를 보고 반박**할 수 있습니다. 리뷰에는 **거짓 경보**(실제로는 문제가 아닌데 문제라고 한 것)가 섞이기 마련이라, 반박으로 걸러내면 결과가 정확해집니다. 이게 팀을 쓰는 가장 큰 이유입니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| 반박 | 다른 팀원의 결론이 틀렸다고 **근거를 들어** 말하기 |
| 철회 | 반박을 받고 증명하지 못하면 그 주장을 **취소** |
| 메신저 (Mailbox) | 팀원끼리 **이름으로** 메시지를 주고받는 기능. 자동으로 배달됨 |

### 4-1. 반박 회의 (15분)
리뷰 팀이 아직 살아 있으면 그대로, 퇴근했다면 다시 뽑아서:

💬 **클로드 대화창**
```
리뷰 팀원 3명에게 전달해줘: docs/review-team.md 를 같이 읽고,
다른 팀원이 찾은 문제 중 과장됐거나 틀렸다고 생각하는 것을 그 팀원에게 직접 반박해.
반박당한 팀원은 재현으로 증명하거나 철회해. 합의된 결과로 review-team.md 를 고쳐줘.
```
👀 **확인할 것**: 현황판에서 팀원끼리 메시지가 오가는 것 (누가 누구에게 보냈는지)

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

반박의 대상은 주로 "추측"이나 "코드"로 표시된 항목입니다. 3-3 의 실제 결과를 기준으로 하면 반박이 붙기 쉬운 항목은 이렇습니다. 큰 요청 본문으로 메모리를 고갈시킨다는 항목은, 서버가 죽은 이유가 메모리 때문인지 JSON 파싱 실패 때문인지 구분하지 못했다고 스스로 적었습니다. XSS 는 코드로만 확인했습니다. 문자열 id `'1'` 로는 책을 못 찾는다는 항목과 `lateFee` 가 `NaN` 을 낸다는 항목은 실행하지 않았습니다. 반박을 받은 팀원은 재현해서 증명하거나, 심각도를 낮추거나, 철회합니다. 결과적으로 review-team.md 의 "추측"이 줄고 "재현"이 늘면 정답입니다. 몇 개가 바뀌는지는 반마다 다릅니다.

이 단계가 보여주는 건 **팀만 할 수 있는 일**입니다. 심부름꾼은 보고하고 사라지기 때문에 다른 심부름꾼의 결과를 볼 수 없고, 서로 반박할 수도 없습니다. 팀원은 메신저로 서로 이름을 불러 직접 따지고, 팀장은 합의된 결과만 정리합니다. 리뷰에 거짓 경보가 섞이는 건 피할 수 없으니, 그걸 걸러 내는 장치가 있다는 게 팀의 값어치입니다. 혼자 리뷰에서 나온 `__proto__` 같은 거짓 경보가 여기서 걸러지는 대표적인 예입니다.

</div>

### 4-2. 내가 직접 끼어들기 (10분)

💡 **왜 하나요?** 모든 걸 팀장을 거쳐 전달하면 느리고 말이 바뀝니다. 팀원에게 **직접** 물어볼 수 있습니다.

`perf` 팀원 화면으로 (↑↓ → **Enter**) 💬
```
"서버가 죽는 문제"가 있다면 그게 제일 급해. 재현 명령어를 정확히 알려줘.
```
👀 **확인할 것**: 팀장을 거치지 않고 perf 가 바로 답함

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

perf 가 돌려줄 정답은 서버를 죽이는 요청들입니다. 실제 결과에서 나온 것은 다음과 같습니다.

```bash
curl -XPOST localhost:3000/api/login -d '{bad'   # 잘못된 JSON → JSON.parse 예외로 서버 종료 (P1)
curl -XPOST localhost:3000/api/login -d '{}'     # 아이디 없이 로그인 → Buffer.from(undefined) 예외로 서버 종료
curl --path-as-is localhost:3000//               # 이상한 주소 → new URL 예외로 서버 종료
```

`data/books.json` 이 깨져 있으면 검색 한 번에 서버가 죽는다는 것도 함께 나옵니다. 셋 다 로그인 없이 요청 한 번이면 되기 때문에, 고칠 순서에서 맨 앞에 와야 합니다.

팀원에게 직접 묻는 이유는, perf 가 자기가 조사하면서 본 것을 전부 기억한 채로 답하기 때문입니다. 팀장에게 물으면 팀장은 perf 의 요약만 가지고 있어서 다시 perf 에게 물어봐야 하고, 그 과정에서 명령어가 빠지거나 바뀝니다.

</div>


<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

`docs/fix-plan.md` 의 담당자 배정은 대략 아래처럼 나오면 정답입니다.

| 담당 | 파일 | 고칠 문제 |
|---|---|---|
| books | `src/books.js` | L1 재고 0 대출, L2 음수 연체료, P3 검색 중복, P4 대출 기록 저장 (P2 동기 읽기·쓰기는 선택) |
| auth | `src/auth.js` | S1 비밀번호 해시, S2 중복 가입 거부, S3 비밀번호 비교, S4 서명 토큰 |

이 표를 오전에 만들어 두는 이유는, 오후 구현 팀에서 가장 큰 사고가 **두 팀원이 같은 파일을 동시에 고쳐 서로 덮어쓰는 것**이기 때문입니다. 문제를 파일 기준으로 나누면 팀원끼리 파일이 겹치지 않습니다. `server.js` 는 모든 기능의 주소가 모이는 공통 파일이라 누구 한 명에게 주면 다른 팀원이 기다려야 하므로, 팀원들이 끝난 뒤 팀장이 한 번에 합치게 합니다.

</div>

## 블록 5 | 🛠️ 구현 팀 — 수리 + 예약 기능 (60분)

### 목표
**파일 주인**을 정하고, **계획을 먼저 확인**한 뒤, 팀이 동시에 고치고 기능까지 추가

> 💡 **오전과 다른 점**: 오전엔 읽기만 했지만 이번엔 팀원들이 **동시에 파일을 고칩니다.** 그래서 ① 망쳐도 돌아갈 세이브 ② 파일 주인 ③ 내가 먼저 확인하는 계획, 세 가지 안전장치를 먼저 겁니다.

### 5-1. 안전장치 (10분)

💡 **왜 하나요?**
- **`git status`**: 커밋 안 한 변경이 있으면 팀이 망쳤을 때 **어디로 돌아갈지** 모릅니다
- **허락 목록**: 팀원 3명이 테스트를 돌릴 때마다 "실행해도 돼요?" 를 물으면 **허락 요청 폭탄**이 쏟아집니다. 안전한 명령은 미리 허락해 둡니다

📖 **용어**
| 말 | 뜻 |
|---|---|
| `permissions.allow` | 설정 파일의 **"묻지 말고 해도 되는 명령" 목록** |
| `Bash(npm test:*)` | `npm test` 로 **시작하는** 터미널 명령은 허락 없이 실행 |

⌨️ **터미널**
```bash
git status   # "nothing to commit, working tree clean" 이 나와야 함. 아니면 git add . && git commit 먼저
```
💬 **클로드 대화창**
```
.claude/settings.json 의 permissions.allow 에 "Bash(npm test:*)", "Bash(node --test:*)" 를 추가해줘. 기존 설정은 유지해줘.
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

`git status` 가 `nothing to commit, working tree clean` 이면 정답입니다. `data/books.json` 이 수정됨(`M`)으로 보이면 `git checkout data/books.json` 으로 되돌리고, 그 외 파일이 보이면 커밋부터 합니다. 이 커밋이 "팀이 망쳤을 때 돌아갈 곳"입니다. 팀원 3명이 동시에 고치기 시작하면 무엇이 누구 때문에 바뀌었는지 사람이 추적하기 어렵기 때문에, 시작점을 깨끗하게 찍어 두는 겁니다.

허락 목록을 넣지 않으면, 팀원들의 "이 명령 실행해도 돼요?" 요청이 전부 팀장 화면으로 올라와서 학생이 계속 Enter 만 누르게 됩니다. `npm test` 는 파일을 바꾸지 않는 안전한 명령이라 미리 허락해도 됩니다.

</div>

### 5-2. 파일 소유표 + 할 일 보드 (10분)

💡 **왜 하나요?**
- **파일 소유표**: 팀원은 모두 **같은 폴더**에서 일합니다. 두 명이 같은 파일을 고치면 **서로 덮어씁니다.** 파일마다 주인을 정하면 막을 수 있습니다
- **계획 모드**: 팀원을 뽑기 **전에** 계획부터 보고 확인합니다. 바로 뽑으면 팀원들이 이미 코드를 고치기 시작한 뒤라 되돌리기 어렵습니다
- **팀원은 대화를 모름**: 팀원은 팀장과 내가 나눈 대화를 모릅니다. 그래서 각 팀원에게 줄 **업무 지시서**를 미리 보고 빠진 게 없는지 확인합니다

📖 **용어**
| 말 | 뜻 |
|---|---|
| 계획 모드 (plan mode) | 클로드가 **읽기만 하고 계획을 세우는** 모드. 파일을 고치지 않음 |
| Shift + Tab | 대화창에서 모드를 차례로 바꾸는 키. 화면 아래에 `plan mode` 가 보이면 멈춤 |
| 할 일 보드 | 팀 전체의 할 일 목록. 대기 / 진행 중 / 완료 |
| 선행 작업 | "A 가 끝나야 B 를 시작할 수 있다". 끝나기 전엔 B 가 잠김 |
| 업무 지시서 | 팀원에게 주는 지시: 역할 / 범위 / 배경 / 할 일 / 결과물 |

💬 **클로드 대화창**: **Shift + Tab** 을 눌러 `plan mode` 로 바꾼 뒤
```
docs/fix-plan.md 와 docs/reservation-plan.md 를 바탕으로 구현 팀 계획을 세워줘.
```

## 블록 6 | 🚧 검문소 — 테스트 못 넘으면 완료 금지 (40분)

### 목표
**hook(검문소)** 으로, 팀원이 테스트를 깨뜨린 채 "완료" 하는 걸 **기계적으로** 막기

> 💡 **이 블록을 하는 이유**: 팀원은 "다 했어요!" 하고 쉬려는 경향이 있습니다. 팀원 여럿이 동시에 일하면 내가 일일이 확인할 수 없습니다. 그래서 **"테스트를 통과해야만 완료"** 라는 규칙을 사람 대신 **자동 검문소**에 맡깁니다.

📖 **용어**
| 말 | 뜻 |
|---|---|
| hook (훅) | **정해진 순간에 자동으로 실행**되는 명령. 하네스 강의의 그 검문소 |
| TaskCompleted | 팀원이 할 일을 **"완료"로 표시하려는 순간** 실행되는 hook |
| 종료 코드 (exit code) | 명령이 끝날 때 남기는 숫자. 0 = 성공, 그 외 = 실패 |
| `exit 2` | hook 에서 **2 로 끝나면 → 그 행동을 막음** (완료 거부). 1 은 못 막음 |
| `1>&2` | 명령 결과를 **에러 출력(stderr)** 으로 보내기 → 이 내용이 팀원에게 피드백으로 전달됨 |
| <code>&#124;&#124;</code> | 앞 명령이 **실패하면** 뒤 명령 실행 |

> 📖 `npm test 1>&2 || exit 2` 를 한 문장으로: "**테스트를 돌려서 결과를 팀원에게 보여주고, 실패하면 완료를 막아라**"

### 6-1. 검문소 설치 (10분)

💬 **클로드 대화창**
```
.claude/settings.json 에 TaskCompleted hook 을 추가해줘.
command 는 "npm test 1>&2 || exit 2" 로. 기존 env, permissions 설정은 유지해줘.
```
👀 **확인할 것**: 설정 파일에 이 부분이 들어 있어야 함
```json
"hooks": {
  "TaskCompleted": [
    { "hooks": [ { "type": "command", "command": "npm test 1>&2 || exit 2" } ] }
  ]
}
```
💬 **강사 질문**: "`|| exit 2` 에서 2 대신 1 이면?" → 막지 못함. **2 여야 막는다**

### 6-2. 🔥 일부러 걸려보기 (20분)

💡 **왜 하나요?** 검문소가 진짜로 막는지 보려면 **일부러 실패하는 상황**을 만들어야 합니다. 그래서 팀원에게 "**아직 코드가 지원하지 않는 기능의 테스트**" 를 먼저 쓰게 하고 완료를 시도하게 합니다.

💬 **클로드 대화창**
```

할 일: test/books.test.js 에 "검색어 앞뒤에 공백이 있어도 결과는 같다" 테스트를 추가해
(예: searchBooks(' 리팩터링 ') 의 결과가 1권). src/books.js 는 고치지 말고 테스트만 추가한 다음 할 일을 완료로 표시해.
```
👀 **확인할 것**: 테스트가 실패하므로 **완료 표시가 거부**되고, tester 가 실패 메시지를 받는 것

이어서 💬
```

```
👀 **확인할 것**: 이번엔 완료 ✅

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

지금 코드에서 `searchBooks(' 리팩터링 ')` 은 1권이 아니라 **11건**을 돌려줍니다. 앞뒤 공백 때문에 빈 단어 `''` 가 생기고, 빈 단어는 모든 제목에 들어 있는 것으로 판정되어 모든 책이 중복으로 나오기 때문입니다. 그래서 tester 가 쓴 테스트는 실패하고, tester 가 완료를 표시하려는 순간 검문소가 `npm test` 를 돌려 실패를 확인하고 `exit 2` 로 완료를 거부합니다. 테스트 실패 메시지는 `1>&2` 로 에러 출력에 실렸기 때문에 tester 에게 그대로 전달되고, tester 는 그걸 읽고 원인을 압니다. 두 번째 지시 후 tester 가 `split(/\s+/).filter(Boolean)` 처럼 빈 단어를 없애도록 고치면 테스트가 통과하고 완료가 받아들여집니다.

블록 5 에서 books 팀원이 검색을 이미 고쳤다면 이 테스트는 처음부터 통과해서 거부가 일어나지 않습니다. 그때는 아직 안 고친 다른 문제로 주제를 바꾸세요. 예를 들어 "기한 안에 반납하면 연체료는 0원이다"(L2)나 "재고 0인 책은 대출이 거부된다"(L1) 중 남은 것을 고르면 됩니다.

검문소가 필요한 이유는 1-2 에서 Edit 를 뺀 것과 같은 원리입니다. "테스트 통과시키고 완료해"라고 말로 시키면 팀원이 가끔 건너뜁니다. 검문소는 말이 아니라 **구조로** 막습니다. 팀원이 여럿일수록 사람이 일일이 확인할 수 없으니 이런 자동 장치의 가치가 커집니다. `exit 1` 이 아니라 `exit 2` 여야 하는 이유는, Claude Code 가 hook 의 종료 코드 2 만 "막아라"로 읽기 때문입니다.

</div>



### 7-2. 🔬 가설 토론 팀 (17분)

💡 **왜 git 기록을 금지하나요?** `git log`·`git diff`(📖 바뀐 내용 비교)·`git show` 를 보면 짝꿍이 바꾼 줄이 바로 보여서 **토론 없이 답을 알게** 됩니다. 오늘은 토론 연습이 목적입니다.

💬 **클로드 대화창** (내 컴퓨터, 팀 켜진 대화)
```
사용자 증상: (증상 카드 내용)
agent team 으로 팀원 3명(모델 Sonnet)을 뽑아서 각자 다른 가설을 조사하게 해줘.
과학 토론처럼 서로의 가설을 반박하려고 노력하게 하고, git 기록은 보지 말고 코드와 실행으로만 증명해.
합의된 원인과 증거(재현 명령어)를 docs/findings.md 에 정리해줘. 아직 고치지는 마.
```
→ 시간 재기 ⏱️ → 찾으면 짝꿍에게 확인 → 맞으면 🎉

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

결과는 짝꿍이 심은 버그에 따라 다르지만, 진행 모양은 비슷합니다. 팀원 3명이 "books.js 의 계산 로직이 틀렸다", "server.js 에서 주소나 값을 잘못 넘긴다", "화면이 잘못된 값을 보여준다"처럼 서로 다른 가설을 맡고, 각자 재현 명령으로 자기 가설을 증명하거나 남의 가설을 깨려고 합니다. 반박에서 살아남은 가설 하나와 그걸 보여주는 재현 명령이 `docs/findings.md` 에 남으면 정답입니다.

이 블록이 팀에 유리한 이유는 **닻 내림 효과** 때문입니다. 클로드 한 명에게 시키면 처음 찾은 그럴듯한 원인에서 멈추는 경우가 많습니다. 한 번 "이게 원인이다"라고 생각하면 그 뒤 조사가 전부 그 생각을 확인하는 쪽으로 기울기 때문입니다. 팀원이 서로 다른 가설을 맡아 반박하면, 증거로 버틴 원인만 남습니다. 시간이 남으면 같은 증상을 혼자 클로드에게도 시켜 보고 걸린 시간과 맞혔는지를 비교하면, 블록 3 처럼 숫자로 근거를 남길 수 있습니다.

git 기록을 금지한 이유는 `git log` 나 `git diff` 를 보면 짝꿍이 바꾼 줄이 바로 보여서 토론 없이 답이 나오기 때문입니다. 실제 현장에서는 git 기록이 가장 빠른 단서이므로 당연히 써야 한다는 점도 같이 말해 주세요. 오늘은 토론 연습이 목적이라 막은 것입니다.

## 블록 8 | 🚀 나만의 팀 — 2바퀴 (90분)

### 목표
**강사 없이** 내가 팀장이 되어, **팀이 필요한지 판단하는 것부터** 퇴근까지 직접

> 💡 **이 블록을 하는 이유**: 1바퀴는 "따라 하기" 였습니다. 실제로 쓸 때는 **"이 일에 팀이 필요한가?"** 부터 내가 정해야 합니다. 그 판단을 혼자 해보는 게 오늘의 마무리입니다.

### 8-1. 고르기 + 팀 설계서 (20분)
| 난이도 | 상황 | 팀 구성 힌트 |
|---|---|---|
| ⭐ | 도서 앱 **README·API 문서 리뷰** | 초보 사용자 / 개발자 / 깐깐한 편집자 |
| ⭐ | **기술 조사**: "이 앱을 SQLite(📖 파일 하나로 된 작은 데이터베이스)로 옮기면?" | 찬성 / 반대 / 옮기는 방법 설계 |
| ⭐⭐ | 도서 앱에 **관리자 기능**(책 추가·삭제) | books / auth / web, 파일 주인 |
| ⭐⭐ | 도서 앱 **테스트 늘리기** | 모듈별 테스트 담당 + 블록 6 검문소 |
| ⭐⭐ | **이전 수업 프로젝트**(메모 앱 등) 보안·성능·테스트 리뷰 | 블록 3 역할 카드 재사용 |
| ⭐⭐⭐ | **내 프로젝트**에 새 기능 | 직접 설계, 파일 소유표 필수 |

**팀 설계서** (종이나 `docs/team-design.md`) — 강사 확인 후 시작
```
① 왜 팀이어야 하나? (혼자·심부름꾼으로 안 되는 이유 한 줄)
② 팀원: 이름 / 역할 / 모델 / 맡을 파일
③ 할 일 보드 초안: 팀원당 4~6개, 선행 작업
④ 결과물: 어떤 파일에 무엇이 남는가
⑤ 안전장치: 시작 전 커밋, 검문소(hook) 필요 여부
```
> 💡 **①이 제일 중요한 이유**: ①에 답을 못 하면 그 일은 혼자나 심부름꾼으로 하는 게 더 싸고 빠릅니다.

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

① 을 확인할 때는 오늘 본 근거로 판단합니다. 좋은 답은 "관점이 서로 달라서 반박이 필요하다(SQLite 찬반 조사)", "파일이 겹치지 않게 셋으로 나뉜다(관리자 기능: books / auth / web)"처럼 블록 2·3·5·7 에서 팀이 이긴 이유 중 하나를 댑니다. 약한 답은 "빨리 하려고", "많이 찾으려고"입니다. 블록 3 에서 팀이 더 많이 찾지는 않았다는 걸 이미 봤기 때문입니다.

메뉴별로 보면 이렇습니다. README·API 문서 리뷰는 관점이 셋이라 팀 연습은 되지만, 문서가 작아서 혼자로도 충분할 가능성이 큽니다. 비교해 보고 그 결론을 회고에 쓰게 하면 좋습니다. SQLite 조사는 찬성·반대가 서로 반박해야 결론이 나므로 팀에 잘 맞습니다. 관리자 기능은 블록 5 와 같은 구조라 파일 소유표만 지키면 팀이 맞습니다. 테스트 늘리기는 모듈별로 서로 대화할 필요가 적어서 심부름꾼 여러 명으로도 됩니다. 학생이 이걸 스스로 알아채면 오늘 목표를 달성한 것입니다.

</div>

## 부록 B | 자주 막히는 곳

| 증상 | 해결 |
|---|---|
| `git clone` 에서 `repository not found` | 폴더 주소(`/tree/main/...`)를 넣음 → `https://github.com/NujabesCode/library-app.git` |
| `git clone` 에서 `Too many arguments` | 주소 뒤에 단어가 2개 이상 → 주소만 |
| 💬 문장을 터미널에 붙여넣어 에러 | 💬 는 `claude` 실행 **후** 대화창에 |

| 팀원 화면에서 Esc → 팀원이 멈춤 | 팀원 화면의 Esc = 그 팀원 작업 중단. "계속해" 라고 말하기 |
| 팀장이 직접 코드를 씀 | 💬 `팀원들이 끝날 때까지 기다려. 직접 구현하지 마` |
| 팀장이 일이 남았는데 끝났다고 함 | 💬 `할 일 보드에 남은 일이 있어. 계속 진행해` |
| 할 일이 계속 "진행 중" | 실제로 끝났는지 확인 → 💬 `○번 일을 완료로 바꿔줘` |
| 허락 요청이 계속 뜸 | `permissions.allow` 에 `Bash(npm test:*)` 등록 (블록 5-1) |
| 두 팀원이 같은 파일을 덮어씀 | 파일 소유표를 지시서에 명시. ⌨️ `git diff` 로 확인 후 복구 |
| hook 이 완료를 안 막음 | 명령이 `exit 2` 로 끝나는지 확인 (1 이면 못 막음) |
| 모든 할 일이 완료 거부됨 | 테스트가 원래 깨져 있음 → 먼저 `npm test` 를 통과 상태로 |
| `/resume` 했더니 팀원이 없음 | 알려진 한계. 💬 "새 팀원을 뽑아줘" |
| 사용량 한도 도달 | 팀원 수 줄이기, Sonnet, 끝난 팀원 퇴근 → 그래도 안 되면 짝꿍 화면으로 |
| 분할 화면이 안 됨 | Windows Terminal·VS Code 터미널은 미지원 → 기본(한 화면) 모드 |
