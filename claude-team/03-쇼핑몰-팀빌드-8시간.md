# 8시간 실습 — 클로드 팀으로 쇼핑몰 처음부터 만들기 (강사용)

> 빈 폴더에서 시작해 무신사·쿠팡 같은 **진짜 쇼핑몰 수준의 사이트**(가상 브랜드 **하루마켓**)를 클로드 팀으로 만듭니다. 블록마다 **목표**(왜 하는지) → 단계마다 **실습 코드**(⌨️ 터미널 / 💬 클로드 대화창, 줄 끝 `#` 은 설명) → **🧑‍🏫 강사 해설** 순서입니다.

---

## 블록 0 | 오리엔테이션 — 빈 폴더에서 시작 (20분)

**목표** — 오늘은 고칠 앱이 없습니다. 빈 폴더 하나에서 시작해, 하루가 끝나면 상품 목록·검색·상세·장바구니·주문·마이페이지가 모두 돌아가는 쇼핑몰이 남습니다. "팀에게 한 방에 시키면 망가지고, 순서를 지키면 버그 없이 나온다"를 직접 겪는 것이 오늘의 핵심입니다.

### 0-1. 프로젝트 폴더 만들기 (10분)

⌨️ **터미널**
```bash
node --version                                  # v20 이상이면 OK (오늘 쓰는 Vite·Playwright 가 20 이상 필요)
claude --version                                # Claude Code 설치 확인. 오래됐으면 claude update
mkdir -p ~/projects/haru-market && cd ~/projects/haru-market   # 빈 프로젝트 폴더 만들고 들어가기
git init                                        # 이 폴더를 git 저장소로 → 오늘 모든 단계를 커밋으로 남김
mkdir -p .claude docs                           # 클로드 설정 폴더와 설계 문서 폴더
```

💬 **클로드 대화창** (⌨️ `claude` 로 시작한 뒤)
```prompt
.claude/settings.json 을 만들어줘. env 에 CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1,   # 팀 기능 켜기 (이 프로젝트에서만)
permissions.allow 에 "Bash(npm run *)", "Bash(npm test*)", "Bash(npx playwright test*)", "Bash(git status*)", "Bash(git diff*)", "Bash(git log*)" 추가.   # 안전한 명령은 묻지 않고 실행 → 허락 요청 폭탄 방지
저장 후 파일 전체를 보여줘.   # 눈으로 확인
```

⌨️ **터미널**
```bash
/exit                                           # (💬 대화창에서) 새 설정을 읽게 클로드 끄기
claude                                          # 다시 켜기 → 이제 팀 기능이 켜진 상태
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

`.claude/settings.json` 에 `env` 와 `permissions.allow` 두 칸이 들어가면 정답입니다. 블록 0 에서 미리 허락 목록을 넣는 이유는, 오늘은 팀원 3~4명이 각자 `npm test`, `npm run build` 를 수십 번 돌리기 때문입니다. 허락 목록이 없으면 그 요청이 전부 팀장 화면으로 올라와서 학생이 계속 Enter 만 누르게 됩니다. `git push`, `rm` 같은 되돌리기 어려운 명령은 일부러 넣지 않았습니다.

설정을 넣은 뒤 반드시 껐다 켜야 합니다. 클로드는 켜질 때 설정을 읽기 때문에, 이걸 빼먹으면 블록 1 에서 팀 대신 심부름꾼이 생깁니다.

</div>

### 0-2. 오늘 만들 것 보여주기 (10분)

⌨️ **화면에 띄우고 같이 읽기** (실제로 치는 명령 아님)
```prompt
하루마켓 = 가상 쇼핑몰 브랜드 (실제 회사 이름·로고 사용 금지)                 # 저작권·상표 문제 없게 가상 브랜드
홈: 배너 슬라이드, 타임특가(카운트다운), 카테고리 바로가기, 랭킹 TOP 10         # 쿠팡·지마켓 첫 화면 느낌
목록: 카테고리별 상품, 정렬(인기·낮은가격·높은가격·할인율), 가격 필터, 페이지 나누기   # 무신사 목록 느낌
검색: 검색창 자동완성, 결과 없을 때 안내                                       # 실제 쇼핑몰 필수 기능
상세: 이미지, 할인가, 별점·리뷰, 옵션(사이즈/색상), 수량, 장바구니·바로구매       # 상품 상세
장바구니 → 주문(가짜 결제) → 주문 완료 → 마이페이지 주문내역                     # 돈이 오가지 않는 가짜 결제
회원: 가입·로그인·로그아웃, 찜(위시리스트), 최근 본 상품                         # 로그인해야 쓸 수 있는 기능
모바일 화면에서도 깨지지 않기                                                   # 반응형
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

학생들에게 먼저 "이걸 클로드에게 한 문장으로 '무신사 같은 쇼핑몰 만들어줘' 하면 어떻게 될까요?"라고 물어보세요. 답은 "뭔가 나오긴 하는데, 장바구니 숫자가 안 맞거나, 로그인하면 화면이 깨지거나, 다시 켜면 데이터가 사라지는" 결과입니다. 팀으로 한 방에 시키면 더 나빠집니다. 팀원마다 상품 데이터 모양을 다르게 상상하고 만들기 때문에, 합치는 순간 화면과 서버가 서로 말이 안 통합니다.

그래서 오늘은 순서를 지킵니다. **설계 팀이 계약서를 쓰고(블록 1) → 내가 확정하고(블록 2) → 팀장 혼자 뼈대를 만들고(블록 3) → 그 위에서 구현 팀이 파일을 나눠 만들고(블록 4) → QA 팀원이 사용자처럼 끝까지 눌러 보고(블록 5) → 리뷰 팀이 털고(블록 6) → 고치고 다듬고(블록 7) → 처음 받는 사람처럼 검증합니다(블록 8).** 이 순서 자체가 "버그 없이 만드는 방법"이고, 오늘 배우는 내용입니다.

실제 회사 이름과 로고를 쓰지 않는 이유도 짚어 주세요. 무신사·쿠팡의 로고나 상호를 그대로 쓰면 상표 문제가 생기고, 포트폴리오에도 쓸 수 없습니다. "느낌은 참고하되 브랜드는 내 것"이 원칙입니다. 상품 이미지는 외부 사진 대신 **그라데이션 + 이모지**로 만들어서 저작권과 인터넷 연결 문제를 동시에 피합니다.

</div>

## 블록 1 | 설계 팀 — 계약서부터 (40분)

**목표** — 코드를 한 줄도 쓰기 전에 팀으로 설계 문서를 만듭니다. 팀원들이 나중에 각자 다른 파일을 만들어도 합쳐지는 건 **모두가 같은 계약서(데이터 모양, API 주소, 화면 목록)를 보고 만들기 때문**입니다. 기획은 파일을 고치지 않아서 팀이 가장 안전하게 잘하는 일이기도 합니다.

### 1-1. 설계 팀 꾸리기 (25분)

💬 **클로드 대화창**
```prompt
"하루마켓"이라는 가상 쇼핑몰을 처음부터 만들 거야. 무신사·쿠팡 같은 수준이 목표고, 실제 브랜드 이름·로고는 쓰지 않아.   # 팀원은 이 대화를 모르니 배경을 직접 적기
기능: 홈(배너 슬라이드, 타임특가 카운트다운, 카테고리, 랭킹), 카테고리 목록(정렬·가격 필터·페이지), 검색(자동완성),   # 0-2 의 기능 목록 그대로
상품 상세(옵션·수량·별점·리뷰), 장바구니, 주문(가짜 결제), 주문 완료, 마이페이지(주문내역·찜·최근 본 상품), 회원가입·로그인. 모바일 대응.
기술: 프론트 React + Vite + react-router, 백엔드 Node + Express, 데이터는 서버 메모리 + JSON 파일 저장, 이미지는 그라데이션+이모지.   # 기술을 미리 못 박아야 팀원끼리 안 갈림
agent team 으로 설계 팀 4명을 뽑아줘. 모델은 모두 Sonnet. 코드는 쓰지 마.   # 이번 블록은 문서만
- pm: 화면 목록과 화면별 기능, 사용자 흐름(검색→상세→장바구니→주문→마이페이지)을 docs/spec.md 에   # 무엇을 만드나
- arch: 데이터 모양(상품·옵션·회원·장바구니·주문)과 API 계약(주소, 요청, 응답 JSON 예시, 에러 코드)을 docs/api.md 에   # 화면과 서버가 지킬 약속
- designer: 색·글꼴·간격·버튼·카드 규칙과 공통 컴포넌트 목록(Header, ProductCard 등)을 docs/design.md 에   # 화면이 한 사이트처럼 보이게
- critic: 세 문서를 읽고 빠진 경우(품절, 재고 부족, 비로그인, 새로고침, 빈 장바구니, 가격 계산)를 찾아서 해당 팀원에게 직접 반박   # 악마의 변호인
서로 문서를 읽고 메시지로 맞춰. 끝나면 세 문서가 서로 어긋나는 곳이 없는지 네가 확인하고 요약해줘.   # 팀장의 최종 대조
```

⌨️ **팀이 일하는 동안**
```prompt
↓ (입력창을 비운 채) → critic 고르고 Enter   # critic 화면 열기 (↑ 는 이전 입력이 나옴)
가격 계산에서 실수가 날 만한 곳만 골라서 arch 에게 다시 물어봐   # critic 에게 직접 지시
Esc                                          # 팀장 화면으로 (팀원 작업이 멈추면 다시 들어가 "계속해")
Ctrl + T                                     # 할 일 보드 보기
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

결과로 `docs/spec.md`, `docs/api.md`, `docs/design.md` 세 파일이 생기면 정답입니다. 잘 나온 결과에는 이런 것들이 들어 있습니다.

- **spec.md** — 화면 9~11개(홈, 카테고리, 검색, 상세, 장바구니, 주문서, 주문 완료, 로그인/가입, 마이페이지)와 각 화면의 기능, 비로그인일 때 어떻게 되는지.
- **api.md** — `GET /api/products?category=&sort=&minPrice=&maxPrice=&page=`, `GET /api/products/:id`, `GET /api/search/suggest?q=`, `POST /api/auth/signup`, `POST /api/auth/login`, `GET/POST/PATCH/DELETE /api/cart`, `POST /api/orders`, `GET /api/orders`, `GET/POST/DELETE /api/wishlist` 같은 주소와, 각각의 요청·응답 JSON 예시, 에러 모양(`{ "error": { "code": "OUT_OF_STOCK", "message": "..." } }`).
- **design.md** — 브랜드 색, 글꼴, 간격 단위(4px/8px), 카드 모양, 할인율 빨간 글씨, 버튼 종류, 공통 컴포넌트 목록.

critic 의 반박에서 꼭 나와야 할 것은 **가격은 서버가 계산한다**는 원칙입니다. 화면이 계산한 가격을 그대로 주문에 쓰면, 사용자가 브라우저에서 값을 바꿔 1원에 주문할 수 있습니다. 그리고 **돈은 정수(원 단위)로만** 다룬다는 원칙입니다. 할인율 계산에서 소수점이 생기면 장바구니 합계가 1원씩 어긋나는 버그가 생깁니다. 이 두 가지가 api.md 에 들어가면 critic 이 제 몫을 한 것입니다.

팀으로 설계하는 이유는 관점이 서로 독립적이기 때문입니다. 혼자 설계시키면 화면 목록은 잘 나오지만 "품절 상품을 장바구니에 담아 둔 상태에서 주문하면?" 같은 경우를 잘 놓칩니다. critic 이 다른 팀원에게 직접 따지면서 이런 구멍이 문서 단계에서 막힙니다. 코드를 쓰기 전에 막는 버그가 가장 싼 버그입니다.

</div>


여기서 커밋하는 이유는, 블록 2 에서 학생이 문서를 직접 고치기 때문입니다. 커밋을 해 두면 `git diff` 로 "팀이 쓴 것"과 "내가 고친 것"이 구분되어 보입니다. 팀원을 바로 퇴근시키는 이유는, 설계 팀은 이제 할 일이 없는데 살아 있으면 팀장이 진행 상황을 물을 때마다 깨어나서 자기 대화 전체를 다시 읽으며 사용량을 쓰기 때문입니다.

## 블록 2 | 계약 확정 — 내가 읽고 고치고 못 박기 (30분)

**목표** — 팀이 쓴 설계를 내가 직접 읽고 확정합니다. 그리고 앞으로 모든 팀원이 자동으로 읽는 규칙 파일 `CLAUDE.md` 를 만듭니다. 팀원은 팀장과 나눈 대화를 모르지만 `CLAUDE.md` 는 켜질 때 자동으로 읽기 때문에, 여기에 적은 규칙은 모든 팀원이 지킵니다.

### 2-1. 설계 검토 (15분)

💬 **클로드 대화창**
```prompt
docs/spec.md, docs/api.md, docs/design.md 를 읽고, 서로 어긋나는 곳과 애매한 곳을 표로 뽑아줘.   # 사람이 보기 전에 한 번 더 대조
특히 api.md 의 응답 JSON 필드 이름이 spec.md 의 화면에서 쓰는 이름과 같은지,   # 필드 이름 불일치 = 합칠 때 가장 흔한 버그
가격·할인·재고·주문 합계 계산 규칙이 한 곳에만 정의돼 있는지 확인해.   # 계산 규칙이 두 군데 있으면 언젠가 달라짐
```

→ 표를 보고 학생이 직접 결정해서 💬 `1번은 A 로, 2번은 B 로 정하고 문서에 반영해줘` 처럼 지시

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

보통 5~10개의 어긋남이 나옵니다. 자주 나오는 것은 이런 것들입니다. 화면에서는 `salePrice` 라고 부르는데 API 에서는 `discountedPrice`, 상품 id 가 어떤 곳은 숫자이고 어떤 곳은 문자열, 장바구니에 담는 단위가 "상품"인지 "상품+옵션 조합"인지 애매함, 품절 옵션을 화면에서 숨길지 회색으로 보여줄지 정해지지 않음.

이걸 **학생이 직접 정하게 하는 게** 이 단계의 핵심입니다. 클로드에게 "알아서 정해"라고 하면 정해지긴 하지만, 오후에 팀원이 만들다가 막혔을 때 학생이 "그거 왜 그렇게 했지?"를 모릅니다. 계약은 사람이 서명하는 것이라고 비유하면 됩니다.

</div>

### 2-2. CLAUDE.md — 모든 팀원이 읽는 규칙 (15분)

```prompt
↓ → qa 고르고 Enter                           # qa 화면: 팀원들의 e2e 추가 요청을 받고 있는지
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

"고치기 전에 그 버그를 잡는 테스트부터"가 이 블록의 원칙입니다. 테스트가 먼저 실패하고, 고친 뒤 통과하면 그 버그는 다시 생겨도 검문소가 막습니다. 이 순서 없이 고치기만 하면 다음 수정 때 같은 버그가 조용히 돌아옵니다.

이 블록에서 팀원끼리 메시지를 주고받는 장면이 자연스럽게 나옵니다. order 가 qa 에게 "로그아웃 후 장바구니 숫자 테스트 추가해 줘"라고 요청하고, qa 가 테스트를 추가하면 order 가 고칩니다. 심부름꾼은 서로 대화하지 못하므로 이런 협업은 팀에서만 됩니다.

다듬기 항목을 버그 수리 **뒤에** 두는 이유도 설명해 주세요. 화면을 화려하게 만드는 일은 끝이 없어서, 먼저 시작하면 버그 수리가 밀립니다. 그리고 다듬기도 검문소와 E2E 를 통과해야 하므로, 화려해지는 동안 기능이 깨지지 않습니다.

마지막 `npm run e2e` 전체가 모두 통과하면 정답입니다. 1~2개가 남으면 블록 8 에서 같이 봅니다.

</div>

### 7-2. 전원 퇴근 + 저장 (15분)

💬 **클로드 대화창**
```prompt
팀원 모두 퇴근시켜줘. qa 도 포함.   # 오늘 팀은 여기까지
```

⌨️ **터미널**
```bash
npm test && npm run build && npm run e2e     # 세 가지 모두 통과해야
git add . && git commit -m "fix: 수리 + 다듬기 완료"   # 최종 세이브
git log --oneline | wc -l                    # 오늘 쌓인 커밋 개수 (보통 40~70개)
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

커밋 개수를 세게 하는 이유는, 학생이 손으로 쳤다면 며칠 걸렸을 작업이 하루에 쌓였다는 걸 숫자로 보여 주기 위해서입니다. 동시에 "이 커밋들을 내가 다 읽었는가?"도 물어 주세요. 답은 대부분 "아니요"입니다. 그래서 블록 8 의 검증이 필요합니다. 내가 다 읽지 못한 코드를 믿으려면, 처음 받는 사람의 자리에서 돌려 보는 확인이 있어야 합니다.

</div>

## 블록 8 | 최종 검증 — 처음 받는 사람처럼 (40분)

**목표** — 지금 폴더에서 되는 건 "내 컴퓨터에서만" 될 수도 있습니다. 완전히 새 폴더에 복사해서 설치부터 다시 해 보고, 사람이 직접 처음부터 끝까지 써 봅니다. 팀이 만든 결과물을 믿을 수 있는지 마지막으로 확인하는 단계입니다.

### 8-1. 새 폴더에서 처음부터 (20분)

⌨️ **터미널**
```bash
cd ~/projects
git clone haru-market haru-check            # 커밋된 것만 새 폴더로 복사 (커밋 안 한 파일은 안 따라옴)
cd haru-check
npm install                                 # 처음 받은 사람처럼 설치부터
npm test && npm run build && npm run e2e    # 세 가지가 새 폴더에서도 통과하는지
npm run dev                                 # 직접 써 보기 → Ctrl + C
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

새 폴더에서도 세 가지가 모두 통과하면 정답입니다. 여기서 자주 걸리는 건 세 종류입니다. 팀원이 라이브러리를 설치만 하고 `package.json` 에 저장하지 않은 경우(새 폴더에서 `Cannot find module`), 데이터 파일이 `.gitignore` 에 걸려 커밋되지 않은 경우(상품이 0개), 팀원이 만든 파일을 아무도 커밋하지 않은 경우입니다. 셋 다 "원래 폴더에서는 되니까 아무도 몰랐던" 버그입니다.

걸린 게 있으면 원래 폴더(`haru-market`)로 돌아가 클로드 혼자에게 고치게 하고, 커밋한 뒤 `haru-check` 에서 `git pull` 로 다시 확인합니다. 이 정도 마무리는 팀이 아니라 **혼자**가 맞습니다. 순서대로 이어지는 작은 수정이라 팀원이 서로 기다리기만 하기 때문입니다.

</div>

### 8-2. 사람이 직접 써 보기 체크 (20분)

⌨️ **브라우저에서 직접** (짝꿍과 바꿔서 서로의 쇼핑몰 써 보기)
```prompt
가입 → 로그인 → 홈 배너·타임특가 확인 → 카테고리 정렬·가격 필터 → 검색 자동완성   # 둘러보기
상세에서 품절 옵션 고르기 → 장바구니 담기 → 수량 바꾸기 → 합계 확인              # 가격 계산
주문 → 주문 완료 → 마이페이지 주문내역 → 같은 상품 재고 줄었는지                 # 주문 흐름
로그아웃 → 장바구니 숫자 → 다시 로그인 → 찜·최근 본 상품                         # 계정 상태
브라우저 창을 휴대폰 폭으로 줄여서 전부 다시                                     # 모바일
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

짝꿍의 쇼핑몰을 써 보게 하는 이유는, 내가 만든 건 내가 아는 길로만 누르기 때문입니다. 남이 쓰면 예상 못 한 순서로 누르다가 버그를 찾습니다. 찾은 게 있으면 짝꿍에게 알려 주고, 그게 E2E 테스트에 없던 흐름이라면 "테스트가 놓친 곳"으로 칠판에 적습니다. 이 목록은 블록 9 회고 때 "다음에 처음부터 테스트에 넣을 흐름"이 됩니다.

여기서 학생들이 거의 버그를 못 찾는다면, 오늘 순서(계약 → 뼈대 → 파일 주인 → 검문소 → E2E → 리뷰 → 수리)가 제대로 작동한 것입니다. "한 방에 버그 없이"는 운이 아니라 이 순서의 결과라는 점을 강조하며 마무리합니다.

</div>

## 블록 9 | 발표 & 회고 (30분)

**목표** — 학생 5~6명이 2분씩 자기 하루마켓을 시연하고, 어디서 팀이 이득이었고 어디서 혼자가 맞았는지 정리합니다.

⌨️ **발표 순서** (한 사람 2분)
```prompt
1) 내 쇼핑몰 시연: 홈 → 검색 → 상세 → 장바구니 → 주문 → 마이페이지   # 결과물
2) git log --oneline 개수와 /usage 로 본 오늘 사용량                    # 비용
3) 팀이 엇나간 순간 하나 + 내가 어떻게 바로잡았나                       # 운영 경험
4) 검문소나 E2E 가 막아 준 버그 하나                                    # 자동 검사의 가치
```

<div class="tnote" markdown="1">

🧑‍🏫 **강사 해설**

오늘 하루를 이렇게 묶어서 정리해 주세요.

| 단계 | 누가 | 왜 그 방식이었나 |
|---|---|---|
| 설계(블록 1) | 🏢 팀 4명 | 관점이 독립적이고 파일을 안 고침. critic 의 반박으로 가격 조작·소수점 버그를 문서 단계에서 막음 |
| 계약 확정(블록 2) | 🧑 나 | 계약은 사람이 서명. CLAUDE.md 로 모든 팀원에게 같은 규칙 |
| 뼈대(블록 3) | 🧑 팀장 혼자 | package.json·라우터 같은 공통 파일은 여럿이 만들면 반드시 덮어씀 |
| 구현(블록 4) | 🏢 팀 3명 | 파일이 겹치지 않게 나눌 수 있어서 동시에 진행 → 가장 큰 속도 |
| E2E(블록 5) | 🏢 qa 1명 | 만든 사람과 검사하는 사람을 분리 |
| 리뷰(블록 6) | 🏢 팀 3명 | 관점별로 깊게, 재현으로 증명 |
| 수리(블록 7) | 🏢 팀 + qa | 버그 목록을 파일 주인별로 나눔. 팀원끼리 테스트 요청 협업 |
| 최종 검증(블록 8) | 🧑 혼자 | 순서대로 이어지는 작은 수정은 팀이 오히려 느림 |

"한 방에 버그 없이"의 정체는 결국 세 가지입니다. **모두가 같은 계약서를 보고 만든다**(블록 1·2), **공통 파일은 한 명만, 나머지는 파일 주인이 따로 있다**(블록 3·4), **사람 대신 기계가 매번 검사한다**(검문소·E2E). 이 셋이 없으면 팀은 혼자보다 버그를 더 많이 만듭니다. 이 셋이 있으면 팀은 혼자보다 몇 배 빠르면서도 덜 틀립니다.

사용량 이야기도 꼭 해 주세요. 오늘은 팀원을 블록마다 뽑고 바로 퇴근시켰습니다. 팀원은 살아 있는 동안 말을 걸 때마다 깨어나 자기 대화 전체를 다시 읽기 때문에, 쓰고 나면 바로 퇴근시키는 습관이 사용량을 가장 크게 아낍니다.

</div>
